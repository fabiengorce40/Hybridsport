# M3 — arbitrage multisport global (Strength + Running + Cross-training + HYROX)

Base : `be7b2c3` (H2.5). M3 n'est **pas** un cinquième moteur sportif : il ne choisit ni exercice, ni allure, ni mouvement, ni station, ni charge, ni répétition. Il lit la semaine placée comme un système et **arbitre** : priorité, placement, proximité, conflits, demandes concurrentes. Code : `packages/planner/src/m3-analysis.ts` (fonctions pures), `m3-policy.ts` (lecture fail-closed), `planner.ts` (boucle d'arbitrage).

## 1. Quatre notions, jamais confondues

| Notion | Source | Rôle dans M3 |
|---|---|---|
| Priorité sportive | ordre DÉCLARÉ des demandes du programme (`rank`) | critère `rank` : le sport le moins prioritaire cède |
| Importance de séance | rôle de composition du moteur (Running KEY / LONG / TEST…) ou archétype déclaré (rôle HYROX H2) → table gouvernée `planner.m3.sessionImportance` | critère `importance` : une séance standard cède face à une séance clé |
| Demande physique | profil CORE (8 structures, `none` / `low` / `moderate` / `high`) | DÉCRIT ; les règles gouvernées décident ce qui est un conflit |
| Proximité | différence d'instants (heures) | une règle a sa fenêtre ; aucun délai déduit d'un niveau |

## 3. Contrat d'arbitrage

Nœud (`M3Node`) : séance (ou historique admis), sport, date, instant, rang, importance, origine (`planned` / `executed` / `abandoned` / `missed` / `history_planned`), profil CORE. Conflit (`M3Conflict`) : règle, structure, membres, plus petit écart. Décision : action, séance, de / vers, partenaire (SWAP), conflit, pourquoi (critère, règle, structure, écart). Résidu : conflit, cause, alternatives essayées.

## 4. Politique gouvernée (aucune matrice codée)

`SPORT A + DEMANDE A + SPORT B + DEMANDE B + ÉCART + PRIORITÉS → DÉCISION` est porté par des PARAMÈTRES :

| Paramètre | Classe | Rôle | Statut actuel |
|---|---|---|---|
| `planner.m3.pairRules` | G2 | détection par paire (sports différents) | TEST_ONLY |
| `planner.m3.accumulationRules` | G2 | succession de jours (tous sports) | TEST_ONLY |
| `planner.m3.neighbourWindowHours` | G2 | distance des voisines transmises | TEST_ONLY |
| `planner.m3.actions` | G2 | `MOVE`, `SWAP`, `RECOMPOSE` (ordre d'essai) — pas de `DROP` | TEST_ONLY |
| `planner.m3.yieldPolicy` | G2 | qui cède (`importance`, `rank`) + `protectPriority` | TEST_ONLY |
| `planner.m3.sessionImportance` | G2 | rôle → clé / standard | TEST_ONLY (facultatif) |
| `planner.m3.historyStatuses` | G2 | historique compté (réalisé ≠ prévu) | TEST_ONLY |
| `planner.m3.maxPasses` | G3 | borne technique | TEST_ONLY |

Absent ⇒ `POLICY_UNAVAILABLE` (tracé `RULE.PLANNER.M3_ARBITRATION_BLOCKED`), comportement V2 inchangé. Profil non dérivable ⇒ `BLOCKED` (`DEMAND_UNAVAILABLE`). PRODUCTION : valeurs `draft` refusées.

Source unique TEST_ONLY : `packages/planner/tests/m3-governance.ts` (reprise par la Beta 0 expérimentale, marquée SIMULATION_ONLY : `BETA0_SIMULATION` inclut les identifiants `planner.m3.*`).

## 5. Boucle d'arbitrage

1. Détection (règles gouvernées) ; conflits triés (le plus proche d'abord, puis identifiant).
2. Qui cède : l'historique jamais ; puis critères gouvernés ; égalité ⇒ personne (résidu `NO_YIELDER`).
3. Actions autorisées dans l'ordre gouverné :
   - **MOVE** : jour libre et disponible, séance RÉGÉNÉRÉE par son moteur, aucun nouveau conflit G4 ni M3, ordre de composition du sport préservé ;
   - **SWAP** : échange de jours avec une séance hors conflit, les deux régénérées ; protection gouvernée (jamais une séance clé ni d'un sport plus prioritaire) ; jamais deux séances composées du même sport ;
   - **RECOMPOSE** : seulement si le moteur consomme des voisines ; la voisine en conflit lui est signalée `key` ; le moteur décide (Strength : priorité de voisine ; Running : aucun levier ⇒ `NO_ENGINE_LEVER` ; CT / H2 : politiques sans importance ⇒ `NO_EFFECT` en pratique).
4. Aucune action ⇒ conflit RÉSIDUEL, visible sur chaque séance (`RECOVERY.PLANNER.M3_CONFLICT_UNRESOLVED`). Jamais de suppression.
5. Après décision : les moteurs consommateurs reçoivent le contexte voisin à jour (refusé ⇒ résidu `NEIGHBOUR_REFRESH`).

Protection contre les boucles : conflit examiné une fois par état ; action acceptée seulement sans nouveau conflit ; signature d'état déjà vue ⇒ `LOOP_DETECTED` ; borne `maxPasses` (une passe = une décision appliquée).

## 6. Sécurité

M3 ne touche que des séances PLANIFIÉES. Une séance refusée (sécurité, gouvernance, douleur) n'est jamais déplacée pour contourner le refus ; une régénération refusée sur un jour candidat est écartée. La douleur reste centrale : planification suspendue (app-core), aucune semaine arbitrée. `WEEK_NOT_REPLACEABLE` intact : une semaine commencée n'est jamais re-planifiée.

## 7. Application (Beta 0)

- `BETA0_PLANNING_VERSION = 'beta0-m3'` : une semaine non commencée d'une version antérieure est régénérée (sûr), une semaine commencée est conservée.
- Semaine persistée : champ additif `arbitration` (statut, passes, version, conflits initiaux, décisions, résidus) ; voisines persistées avec `importance`.
- Historique transmis : `recentOf` porte le statut connu (réalisée, abandonnée, manquée, prévue).
- Planning : une phrase lisible sous la carte d'une séance déplacée, échangée, recomposée ou restée en conflit (aucun code).

## 9. Limites

- `high_intensity_systemic` est `high` pour presque toute séance sous la normalisation des doses TEST_ONLY : exclue des règles TEST (non discriminante).
- Priorités sans égalité possible (ordre total du programme).
- Running n'a aucun levier de recomposition ; CT C3 et H2 n'interprètent pas l'importance des voisines.
- Empreintes HYROX non stockées côté application (anti-doublon non alimenté pour HYROX).
- 7 séances sur 7 jours : seul l'échange reste possible ; la fréquence n'est jamais réduite (aucune politique de DROP).
